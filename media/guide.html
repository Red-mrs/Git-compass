Welcome to Git Compass 🧭

Git Compass is your personal Git cockpit. Everything lives in the compass icon on the left activity bar. This guide explains Git from zero and shows where each action is. Buttons like run the action directly.

Git in 3 minutes

Git is a time machine for your project folder. Whenever you want, you save a snapshot (a commit) of your files. You can look at old snapshots, compare them, undo changes, work on several ideas in parallel (branches), and copy snapshots to/from a server like GitHub (push/pull).

The four places your work lives

  1. Working folder — the normal files you edit. Git notices every change (they appear in Changes).
  2. Staging area — you pick which changes go into the next snapshot. Think of it as a shopping basket. (Don't want to bother? Just press Commit — Git Compass offers to commit everything.)
  3. Commit — a saved snapshot with a message, author and date. Commits are permanent and can always be returned to.
  4. Remote — a copy of the repository on a server (GitHub). Push uploads your commits, Pull downloads others' commits.
💡 Committing is local and instant. Nothing goes to GitHub until you Push (or Sync).

  4. Write a message like "Initial version" in the Overview and press Commit.

💡 Shortcut: works from any folder — it sets up Git, commits your files (after showing what will be uploaded), creates a new private or public GitHub repository and uploads everything in one go. If the folder already has a remote called origin (e.g. a school GitLab), it is kept and GitHub is added as github.

B) Download an existing repository

— pick one of your GitHub repositories (after signing in) or paste a URL. VS Code asks where to save it and opens it.

.gitignore — files Git should never track

Build outputs, node_modules, .env files with passwords, editor junk… Right-click such a file in Changes → Add to .gitignore.

Everyday workflow

1
Get the latest version — if the Overview says commits are waiting, press Pull (or Sync).
2
Work — edit files as usual. They show up under Changes with a letter: M modified, U new (untracked), D deleted.
3
Review — click a file to see a side-by-side diff (red = removed, green = added). Throw away a change you don't want with ↶ Discard.
4
Stage — press + on files that belong together (or skip this: Commit offers to take all changes). You can even stage single lines: select them in the diff → right-click → Stage Selected Lines.
5
Commit — write a short message (what & why) and press Commit (Ctrl+Enter).
6
Sync — press Sync to upload your commits (it first downloads others' commits so nothing clashes).
💡 Commit often, in small logical pieces ("Add login form", "Fix typo in README"). Small commits are easy to understand and easy to undo.

Branches

A branch is a separate line of work. Your main line is usually main. For a new feature or an experiment, create a branch, commit there freely, and when it's done merge it back. If the experiment fails, just delete the branch — main was never touched.

  • Create: — it starts from where you are and you switch to it automatically.
  • Switch: , or double-click a branch label in the Commit Graph. Your files change to that branch's version. Uncommitted changes? Git Compass offers to stash them or bring them along.
  • Merge: switch to the branch that should receive the work (e.g. main), then and pick the feature branch.
  • Rebase (advanced): instead of a merge commit, replays your commits on top of another branch for a straight history. Right-click a branch → Rebase Current Branch onto This.
  • Delete: right-click → Delete. Git warns you if the branch has work that isn't merged anywhere.
  • Remote branches (origin/feature) are the server's branches as of your last fetch. Double-click / Checkout one to get a local branch that tracks it.

Merge vs. rebase — which?

Merge is always safe and keeps history exactly as it happened. Rebase gives a cleaner line but rewrites your commits — never rebase commits that others already have. When unsure: merge.

Working with the remote

FetchAsk the server "what's new?" Downloads information about new commits but does not change your files. Always safe. Git Compass can do it automatically in the background.
Pull ↓Fetch + bring the new commits into your branch and your files.
Push ↑Upload your new commits to the server.
Sync ⟳Pull, then Push. The one button you need most of the time.
Publish branchThe first push of a new branch: creates it on the server and links ("tracks") it.

The Overview shows ↑2 to push (your commits not on the server) and ↓3 to pull (server commits you don't have). Both at once means the branch diverged: Sync will merge them for you (you may get conflicts if you both edited the same lines).

⚠ "Push rejected" means someone pushed before you. Don't force push — just Sync.

Pull strategy

Setting gitCompass.pullStrategy: merge (default, safest), rebase (straight history), or ff-only (only pull when no merging is needed).

Resolving conflicts

A conflict happens when two branches changed the same lines of a file differently and Git can't decide which version is right. It's normal and fixable — nothing is lost.

Step by step

1
The Changes view shows a Merge Conflicts group. The Overview shows an orange banner with Continue / Abort.
2
Click a conflicted file. You'll see blocks like this: 
<<<<<<< HEAD   (Current — your branch)
  color: blue;
=======
  color: green;
>>>>>>> feature  (Incoming — the other branch)
Above each block VS Code shows clickable links: Accept Current · Accept Incoming · Accept Both · Compare. Or edit the text by hand. Or right-click the file → Open in Merge Editor for a 3-pane view.
3
Make sure no <<<<<<<, =======, >>>>>>> lines remain, then save.
4
Press ✓ Mark Resolved on the file (stages it). Shortcut for whole files: Keep Current / Keep Incoming in the right-click menu.
5
When all files are resolved press Continue in the Overview. Changed your mind? Abort returns everything to how it was before.
💡 During a rebase, "Current" is the branch you rebase onto and "Incoming" is your commit being replayed — the opposite of a merge.

💡 Once something is committed, it's almost impossible to really lose it. Undo History remembers every position of your branch for ~90 days.

Stash — put changes aside

Need to switch branch or pull but you're in the middle of something you don't want to commit yet? puts all your changes into a drawer and your folder becomes clean.

  • Apply = take the changes back, keep a copy in the drawer.
  • Pop = take the changes back and remove them from the drawer.
  • Drop = throw the stash away.
  • Create Branch from Stash = start a new branch with those changes.

Expand a stash in the Stashes view to see what's inside (click files to diff).

Worktrees — several branches at once

Normally a repository folder has one branch checked out; switching branches swaps the files in that folder. A worktree is an extra folder connected to the same repository, with a different branch checked out. Both folders share all commits, branches, tags and stashes (there is still only one history) — only the files on disk differ.

When is this useful?

  • You're in the middle of a feature and an urgent fix on main is needed — no stashing, no half-finished commits: open a worktree for main.
  • Reviewing a colleague's branch or a pull request while your own work stays untouched.
  • Running two versions side by side (e.g. compare behaviour, long builds or tests on one branch while coding on another).

How

  1. (or right-click a branch → New Worktree…). Pick a branch — or create a new one — and a folder (by default next to your repository, e.g. my-project-hotfix).
  2. Choose Open in New Window. That window is a normal Git Compass window for that branch: commit, push, pull as usual.
  3. Done? In the Worktrees view press 🗑 Remove. The folder is deleted; the branch and its commits stay.
💡 Rules: a branch can be checked out in only one worktree at a time (Git Compass tells you where it is open and offers to open that folder). Don't delete a worktree folder by hand — if you did, use Prune Missing Worktrees. Lock a worktree that lives on a removable drive so it isn't pruned while unplugged.

Exploring history

Commit Graph

There are two versions: the compact Graph view in the Git Compass sidebar (always visible while you work — you can even drag it into the Explorer or the secondary side bar) and the big editor tab with author/date columns and a details pane.

A visual map of all branches. Each dot is a commit, each colour a line of work; where lines join is a merge. Click a commit to see its details and changed files, right-click commits or branch labels for actions, double-click a branch label to switch to it. Search by message, author, commit ID, changed text or file path.

File History

Open any file and look at the File History view: every commit that touched it (following renames). Click one to see what changed in it. Pin 📌 the view to keep showing one file.

Blame — who wrote this line?

The faint text at the end of the current line says who last changed it, when, and why (commit message). Hover it for links. Toggle full-file blame (with age colours) via the editor title menu or .

Compare

shows commits only in one side and every file that differs. Right-click a branch → Compare with Current Branch is the quickest way to see "what's in this branch that isn't in mine?"

Rewriting history (advanced)

Before you push, you can polish your commits. Rule: only rewrite commits that nobody else has yet (not pushed, or on your own branch).

Edit history (interactive rebase)

Right-click a commit → Edit History from Here…. A visual editor lists the commits from that one up to now (oldest first). For each choose:

Keep (pick)leave it as is
Rewordchange its message (type the new message right there)
Editstop there so you can change its files; then stage and press Continue
Squash ↑melt it into the commit above (messages are combined)
Fixup ↑melt it into the commit above (its message is dropped) — great for "fix typo" commits
Dropremove the commit and its changes

Drag rows to reorder. Press Start. If a conflict appears, resolve it as usual and press Continue — or Abort to get everything back.

Force push

After rewriting commits that were pushed, a normal push is rejected. Force Push (in the ⋯ menu of the Overview) replaces the server's version. Git Compass uses --force-with-lease, which refuses if someone else pushed in the meantime. Still: never force push to a shared main.

Glossary

Repository (repo)
A project folder tracked by Git (the history is stored in the hidden .git folder).
Commit
A saved snapshot of the project with a message, author and date. Identified by an ID (SHA) like 3f9a2c1.
Stage / staging area / index
The set of changes chosen for the next commit.
Branch
A movable label pointing to the latest commit of a line of work.
HEAD
"Where you are now" — usually the current branch.
Detached HEAD
You checked out a commit or tag directly, not a branch. Fine for looking around; create a branch before committing.
Remote / origin
A server copy of the repo. origin is the default name of the main remote.
Upstream / tracking branch
The remote branch your local branch syncs with (e.g. main ↔ origin/main).
Fetch / Pull / Push
Check for / download and apply / upload commits.
Merge
Combine another branch's work into the current branch.
Fast-forward
A merge where your branch simply moves ahead because it had no own new commits.
Rebase
Replay your commits on top of another commit (rewrites them).
Conflict
Both sides changed the same lines; you decide the result.
Cherry-pick
Copy one commit from somewhere onto your current branch.
Revert
A new commit that undoes an earlier one.
Reset
Move the current branch to another commit (soft/mixed keep changes, hard discards).
Stash
A drawer for unfinished changes.
Worktree
A folder with files checked out from the repository. Besides the main one you can add linked worktrees, each on its own branch.
Tag
A permanent name for a commit, typically a release (v1.2.0).
Reflog (Undo History)
Git's log of where HEAD has been — your safety net.
Pull request (PR)
A GitHub request to merge a branch, with discussion and review.
.gitignore
A file listing patterns of files Git should ignore.
